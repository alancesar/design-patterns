# File Transfer

## Description

In File Transfer, each application produces files with the information other applications need and consumes files generated by the others. There is no direct call between systems: the file is the contract. Whoever does the integrating takes care of converting formats, so the producer doesn't need to know the consumer.

Files are usually generated at intervals that make sense for the business (for example, a nightly export) rather than in real time. This makes the style simple and universal, since any system that can read and write files can take part, even if it uses a different language or platform.

Choosing the format (delimited text, fixed width, XML, JSON, legacy mainframe formats) is an important decision, because it determines how much transformation processing is needed and which reading and writing tools are available.

## Problems it solves

- Independently developed applications, written in different languages and on different platforms, need to exchange information.
- One application's output rarely has the format another needs, which requires conversion.
- The frequency of the exchange should follow the pace of the business, not necessarily the technical capacity for real-time communication.
- No access to each system's internals is needed: agreeing on a file format is enough.

## When to use

- The exchange is naturally periodic or batch-based (closings, loads, reports, reconciliations).
- There are legacy or third-party systems that only offer file import and export.
- The systems need to stay decoupled in platform and technology, with low integration cost.
- Large volumes of data are moved at once and latency isn't critical.

### When to avoid

- When data must be up to date in near real time; prefer [Messaging](/architecture/microservices/communication-styles/messaging).
- When you need to invoke behavior in the remote system and get an immediate response; see [Remote Procedure Invocation](/architecture/microservices/communication-styles/remote-procedure-invocation).
- When many systems need to see the same consistent information at all times; see [Shared Database](/architecture/microservices/service-collaboration/shared-database).

## Trade-offs

| Benefit | Cost / Risk |
| --- | --- |
| Low coupling: only the file format is shared | Stale data: it reflects only the last batch generated |
| Any system that reads and writes files can participate | The format and transformation need an owner and documentation |
| Mature tooling for reading, writing, and converting | No built-in confirmed delivery or error handling: partial failures and duplicates are the integration's problem |
| Cheap and easy to deploy | Update conflicts between systems only surface later, during reconciliation |

- **Consistency:** the systems are temporarily out of sync between one exchange and the next.
- **Operations:** you have to deal with file names, locking during writes, archiving, and reprocessing.
- **Observability:** tracking file arrival, volume, and rejection requires dedicated monitoring.

## Diagram

```mermaid
flowchart LR
    A["Application A (producer)"] -->|"writes"| F["File in agreed format"]
    F -->|"reads"| T["Format converter"]
    T --> B["Application B (consumer)"]
```

The producing application writes a file periodically; a converter adapts the format, and the consuming application reads it at its own pace.

## Related patterns

- [Shared Database](/architecture/microservices/service-collaboration/shared-database) — another integration style, with data shared in near real time.
- [Remote Procedure Invocation](/architecture/microservices/communication-styles/remote-procedure-invocation) — synchronous integration through calls to exposed interfaces.
- [Messaging](/architecture/microservices/communication-styles/messaging) — frequent, immediate, asynchronous exchange of small packets of data.
- [Message](/architecture/eip/message-construction/message) — the unit of data that replaces the file in messaging.
- [Message Channel](/architecture/eip/messaging-channels/message-channel) — the channel that plays the role of the place where files are exchanged.
- [Message Endpoint](/architecture/eip/messaging-endpoints/message-endpoint) — the point where the application reads from and writes to the channel.
