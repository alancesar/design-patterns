# Cloud Design Patterns

Personal catalog based on the [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/patterns/), which maintains the catalog originally published in the *Cloud Design Patterns* book (Microsoft patterns & practices, 2014). The patterns are provider-agnostic; Azure appears only in the implementation notes. Each pattern has a description, the problems it solves, when to use it, trade-offs, tags (Well-Architected Framework pillars), and a Mermaid diagram.

Total: 44 patterns in 8 groups. Tags: Well-Architected Framework pillars.

## Messaging (10) {#messaging}

| Pattern | Summary | Tags |
| --- | --- | --- |
| [Asynchronous Request-Reply](/cloud/cloud-design-patterns/messaging/asynchronous-request-reply) | The Asynchronous Request-Reply pattern decouples back-end processing from the front-end host when the work has to run asynchronously but the client still needs a clear response. | [`Performance Efficiency`](/tags/performance-efficiency) |
| [Claim Check](/cloud/cloud-design-patterns/messaging/claim-check) | The Claim Check pattern separates payload storage from message delivery. | [`Reliability`](/tags/reliability) [`Security`](/tags/security) [`Cost Optimization`](/tags/cost-optimization) [`Performance Efficiency`](/tags/performance-efficiency) |
| [Competing Consumers](/cloud/cloud-design-patterns/messaging/competing-consumers) | The Competing Consumers pattern lets multiple consumer instances concurrently process messages received on the same messaging channel. | [`Reliability`](/tags/reliability) [`Cost Optimization`](/tags/cost-optimization) [`Performance Efficiency`](/tags/performance-efficiency) |
| [Idempotent Consumer](/cloud/cloud-design-patterns/messaging/idempotent-consumer) | The Idempotent Consumer pattern designs message consumers so that processing the same message more than once has exactly the same effect as processing it a single time. | [`Reliability`](/tags/reliability) |
| [Messaging Bridge](/cloud/cloud-design-patterns/messaging/messaging-bridge) | The Messaging Bridge connects systems that use different messaging infrastructures (for example, a legacy on-premises broker and a cloud queue service) and relays messages between them. | [`Cost Optimization`](/tags/cost-optimization) [`Operational Excellence`](/tags/operational-excellence) |
| [Pipes and Filters](/cloud/cloud-design-patterns/messaging/pipes-and-filters) | The Pipes and Filters pattern breaks a complex processing task down into a sequence of independent, reusable steps. | [`Reliability`](/tags/reliability) |
| [Priority Queue](/cloud/cloud-design-patterns/messaging/priority-queue) | The Priority Queue pattern prioritizes the requests sent to a service so that higher-priority requests are received and processed before lower-priority ones. | [`Reliability`](/tags/reliability) [`Performance Efficiency`](/tags/performance-efficiency) |
| [Publisher-Subscriber](/cloud/cloud-design-patterns/messaging/publisher-subscriber) | The Publisher-Subscriber (pub/sub) pattern lets an application announce events asynchronously to multiple interested consumers, without knowing who they are. | [`Reliability`](/tags/reliability) [`Security`](/tags/security) [`Cost Optimization`](/tags/cost-optimization) [`Operational Excellence`](/tags/operational-excellence) [`Performance Efficiency`](/tags/performance-efficiency) |
| [Queue-Based Load Leveling](/cloud/cloud-design-patterns/messaging/queue-based-load-leveling) | The Queue-Based Load Leveling pattern places a queue between the tasks that generate work (producers) and the service that performs that work (consumer). | [`Reliability`](/tags/reliability) [`Cost Optimization`](/tags/cost-optimization) [`Performance Efficiency`](/tags/performance-efficiency) |
| [Sequential Convoy](/cloud/cloud-design-patterns/messaging/sequential-convoy) | The Sequential Convoy groups related messages by a category key (for example, an order ID) and processes each group sequentially, one message at a time, while different groups are processed in parallel. | [`Reliability`](/tags/reliability) |

## Data Management (6) {#data-management}

| Pattern | Summary | Tags |
| --- | --- | --- |
| [Cache-Aside](/cloud/cloud-design-patterns/data-management/cache-aside) | Cache-Aside loads data into the cache on demand from the source data store. | [`Reliability`](/tags/reliability) [`Performance Efficiency`](/tags/performance-efficiency) |
| [CQRS](/cloud/cloud-design-patterns/data-management/cqrs) | CQRS (Command Query Responsibility Segregation) separates the operations that change data (*commands*) from the operations that read data (*queries*), using distinct models for each side. | [`Performance Efficiency`](/tags/performance-efficiency) |
| [Event Sourcing](/cloud/cloud-design-patterns/data-management/event-sourcing) | Instead of storing only the current state of the data and overwriting it on every change (the CRUD model), Event Sourcing records the entire sequence of actions applied to an entity as immutable events in an append-only store, the **event store**. | [`Reliability`](/tags/reliability) [`Performance Efficiency`](/tags/performance-efficiency) |
| [Index Table](/cloud/cloud-design-patterns/data-management/index-table) | Many data stores organize entities only by the primary key (or by the partition/shard key). | [`Reliability`](/tags/reliability) [`Performance Efficiency`](/tags/performance-efficiency) |
| [Materialized View](/cloud/cloud-design-patterns/data-management/materialized-view) | The Materialized View pattern generates prepopulated views ahead of time over the data in one or more stores when that data isn't in the ideal format for the required queries. | [`Performance Efficiency`](/tags/performance-efficiency) |
| [Sharding](/cloud/cloud-design-patterns/data-management/sharding) | The Sharding pattern divides a data store into horizontal partitions, called *shards*. | [`Reliability`](/tags/reliability) [`Cost Optimization`](/tags/cost-optimization) |

## Resiliency (6) {#resiliency}

| Pattern | Summary | Tags |
| --- | --- | --- |
| [Bulkhead](/cloud/cloud-design-patterns/resiliency/bulkhead) | The Bulkhead pattern isolates the elements of an application into independent pools, so that if one of them fails, the others keep working. | [`Reliability`](/tags/reliability) [`Security`](/tags/security) [`Performance Efficiency`](/tags/performance-efficiency) |
| [Circuit Breaker](/cloud/cloud-design-patterns/resiliency/circuit-breaker) | The Circuit Breaker temporarily blocks access to a remote service or resource when failures exceed a threshold. | [`Reliability`](/tags/reliability) [`Performance Efficiency`](/tags/performance-efficiency) |
| [Health Endpoint Monitoring](/cloud/cloud-design-patterns/resiliency/health-endpoint-monitoring) | The application exposes health endpoints (for example, `/health` over HTTPS or gRPC's standard health checking protocol) that external tools query at regular intervals. | [`Reliability`](/tags/reliability) [`Operational Excellence`](/tags/operational-excellence) [`Performance Efficiency`](/tags/performance-efficiency) |
| [Rate Limiting](/cloud/cloud-design-patterns/resiliency/rate-limiting-pattern) | The Rate Limiting pattern has an application **control the rate at which it sends requests** to a service that imposes usage limits. | [`Reliability`](/tags/reliability) |
| [Retry](/cloud/cloud-design-patterns/resiliency/retry) | The Retry pattern lets an application handle transient failures when connecting to a remote service or resource by transparently repeating an operation that failed. | [`Reliability`](/tags/reliability) |
| [Throttling](/cloud/cloud-design-patterns/resiliency/throttling) | The Throttling pattern limits the resources that an application instance, a tenant, or an entire service can consume. | [`Reliability`](/tags/reliability) [`Security`](/tags/security) [`Cost Optimization`](/tags/cost-optimization) [`Performance Efficiency`](/tags/performance-efficiency) |

## Distributed Coordination (5) {#distributed-coordination}

| Pattern | Summary | Tags |
| --- | --- | --- |
| [Choreography](/cloud/cloud-design-patterns/distributed-coordination/choreography) | The Choreography pattern distributes the logic of a business flow among the services that take part in it, instead of concentrating it in a central orchestrator. | [`Operational Excellence`](/tags/operational-excellence) [`Performance Efficiency`](/tags/performance-efficiency) |
| [Compensating Transaction](/cloud/cloud-design-patterns/distributed-coordination/compensating-transaction) | The Compensating Transaction pattern undoes work already performed when one or more steps of an eventually consistent operation fail. | [`Reliability`](/tags/reliability) |
| [Leader Election](/cloud/cloud-design-patterns/distributed-coordination/leader-election) | The Leader Election pattern coordinates the actions of a set of collaborating instances of a distributed application by electing one of them as leader. | [`Reliability`](/tags/reliability) |
| [Saga](/cloud/cloud-design-patterns/distributed-coordination/saga) | The Saga pattern maintains data consistency in distributed systems by splitting a business operation that spans several services into a sequence of **local transactions**. | [`Reliability`](/tags/reliability) |
| [Scheduler Agent Supervisor](/cloud/cloud-design-patterns/distributed-coordination/scheduler-agent-supervisor) | The Scheduler Agent Supervisor pattern coordinates a set of distributed actions as a single logical operation: either the entire operation completes successfully, or the work already done is undone. | [`Reliability`](/tags/reliability) [`Performance Efficiency`](/tags/performance-efficiency) |

## Deployment and Topology (5) {#deployment-and-topology}

| Pattern | Summary | Tags |
| --- | --- | --- |
| [Compute Resource Consolidation](/cloud/cloud-design-patterns/deployment-and-topology/compute-resource-consolidation) | The Compute Resource Consolidation pattern groups multiple tasks or operations into a single computational unit (a virtual machine, a container, a hosting plan, or a node pool) instead of keeping each one in a dedicated unit. | [`Cost Optimization`](/tags/cost-optimization) [`Operational Excellence`](/tags/operational-excellence) [`Performance Efficiency`](/tags/performance-efficiency) |
| [Deployment Stamps](/cloud/cloud-design-patterns/deployment-and-topology/deployment-stamp) | The Deployment Stamps pattern consists of deploying multiple independent copies of an application's components, including the data stores, as a single group of resources. | [`Operational Excellence`](/tags/operational-excellence) [`Performance Efficiency`](/tags/performance-efficiency) |
| [External Configuration Store](/cloud/cloud-design-patterns/deployment-and-topology/external-configuration-store) | The External Configuration Store pattern moves configuration information out of the application deployment package and into a centralized repository. | [`Operational Excellence`](/tags/operational-excellence) |
| [Geode](/cloud/cloud-design-patterns/deployment-and-topology/geodes) | The Geode pattern (from **ge**ographical n**ode**) consists of deploying the same set of backend services across multiple geographic nodes around the world, where each node can serve any request from any client, in any region. | [`Reliability`](/tags/reliability) [`Performance Efficiency`](/tags/performance-efficiency) |
| [Static Content Hosting](/cloud/cloud-design-patterns/deployment-and-topology/static-content-hosting) | The Static Content Hosting pattern consists of publishing an application's static content (HTML pages, images, stylesheets, client-side JavaScript, documents, software packages) to a cloud storage service that can deliver it directly to the client over HTTP(S), without going through the application servers. | [`Cost Optimization`](/tags/cost-optimization) |

## Gateways and Edge (4) {#gateways-and-edge}

| Pattern | Summary | Tags |
| --- | --- | --- |
| [Backends for Frontends](/cloud/cloud-design-patterns/gateways-and-edge/backends-for-frontends) | The Backends for Frontends (BFF) pattern proposes creating a separate backend service for each frontend interface (for example, web application, mobile app, embedded devices), instead of using a single general-purpose backend for all of them. | [`Reliability`](/tags/reliability) [`Security`](/tags/security) [`Performance Efficiency`](/tags/performance-efficiency) |
| [Gateway Aggregation](/cloud/cloud-design-patterns/gateways-and-edge/gateway-aggregation) | The Gateway Aggregation pattern uses a gateway to aggregate several individual requests into a single request. | [`Reliability`](/tags/reliability) [`Security`](/tags/security) [`Operational Excellence`](/tags/operational-excellence) [`Performance Efficiency`](/tags/performance-efficiency) |
| [Gateway Offloading](/cloud/cloud-design-patterns/gateways-and-edge/gateway-offloading) | The Gateway Offloading pattern moves shared or specialized features to a gateway (reverse proxy) that would otherwise have to be implemented and maintained in every backend service. | [`Reliability`](/tags/reliability) [`Security`](/tags/security) [`Cost Optimization`](/tags/cost-optimization) [`Operational Excellence`](/tags/operational-excellence) [`Performance Efficiency`](/tags/performance-efficiency) |
| [Gateway Routing](/cloud/cloud-design-patterns/gateways-and-edge/gateway-routing) | The Gateway Routing pattern puts a gateway in front of a set of applications, services, or deployments and exposes everything through a single endpoint. | [`Reliability`](/tags/reliability) [`Operational Excellence`](/tags/operational-excellence) [`Performance Efficiency`](/tags/performance-efficiency) |

## Security and Access (4) {#security-and-access}

| Pattern | Summary | Tags |
| --- | --- | --- |
| [Federated Identity](/cloud/cloud-design-patterns/security-and-access/federated-identity) | The Federated Identity pattern delegates authentication of users (and workloads) to an external, trusted identity provider (IdP) instead of implementing it in the application code. | [`Reliability`](/tags/reliability) [`Security`](/tags/security) [`Performance Efficiency`](/tags/performance-efficiency) |
| [Gatekeeper](/cloud/cloud-design-patterns/security-and-access/gatekeeper) | The Gatekeeper pattern protects applications and services by placing a dedicated component between clients and the system. | [`Security`](/tags/security) [`Performance Efficiency`](/tags/performance-efficiency) |
| [Quarantine](/cloud/cloud-design-patterns/security-and-access/quarantine) | The Quarantine pattern ensures that third-party software artifacts (container images, library packages, infrastructure as code modules, operating system images, vendor installers) are consumed by the workload only after they've been verified and marked as trusted by a well-defined process. | [`Security`](/tags/security) [`Operational Excellence`](/tags/operational-excellence) |
| [Valet Key](/cloud/cloud-design-patterns/security-and-access/valet-key) | The Valet Key pattern gives the client a token or key that grants direct but restricted access to a specific resource, such as a file in an object store or a queue. | [`Security`](/tags/security) [`Cost Optimization`](/tags/cost-optimization) [`Performance Efficiency`](/tags/performance-efficiency) |

## Integration and Modernization (4) {#integration-and-modernization}

| Pattern | Summary | Tags |
| --- | --- | --- |
| [Ambassador](/cloud/cloud-design-patterns/integration-and-modernization/ambassador) | The Ambassador pattern creates helper services that send network requests on behalf of a consumer application or service. | [`Reliability`](/tags/reliability) [`Security`](/tags/security) |
| [Anti-Corruption Layer](/cloud/cloud-design-patterns/integration-and-modernization/anti-corruption-layer) | The Anti-Corruption Layer is a facade or adapter layer placed between subsystems that don't share the same semantics. | [`Operational Excellence`](/tags/operational-excellence) |
| [Sidecar](/cloud/cloud-design-patterns/integration-and-modernization/sidecar) | The Sidecar pattern deploys an application's helper components in a separate process or container that runs alongside the main application. | [`Security`](/tags/security) [`Operational Excellence`](/tags/operational-excellence) |
| [Strangler Fig](/cloud/cloud-design-patterns/integration-and-modernization/strangler-fig) | The Strangler Fig pattern incrementally migrates a legacy system by replacing specific pieces of functionality, one by one, with new applications and services. | [`Reliability`](/tags/reliability) [`Cost Optimization`](/tags/cost-optimization) [`Operational Excellence`](/tags/operational-excellence) |
